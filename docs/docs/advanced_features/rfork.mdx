R-Fork (Tensor Remote Fork) is a novel weight loading methodology that leverages efficient inter-node GPU-to-GPU data transfer path to load tensors from a running SGLang instance to a new instance with zero-copy. It can significantly optimize the SGLang instance boot-up time by reducing model weights loading from several minutes to mere seconds.

To learn more details about R-Fork, please check **<a href="https://lmsys.org/blog/2025-12-10-rfork/"> R-Fork blog </a>**

### NCCL as backend

seed instance:
```shell Command
python -m sglang.launch_server [args]
```

client instance:
```shell Command
python -m sglang.launch_server [args] \
  --load-format remote_instance \
  --remote-instance-weight-loader-seed-instance-ip [seed_instance_ip] \
  --remote-instance-weight-loader-seed-instance-service-port [seed_instance_service_port] \
  --remote-instance-weight-loader-send-weights-group-ports [send_weights_nccl_group_ports_list]  \
  --remote-instance-weight-loader-backend nccl
```

### TransferEngine as backend

seed instance:
```shell Command
python -m sglang.launch_server [args] \
  --remote-instance-weight-loader-start-seed-via-transfer-engine
```

```shell Command
python -m sglang.launch_server [args] \
  --load-format remote_instance \
  --remote-instance-weight-loader-seed-instance-ip [seed_instance_ip] \
  --remote-instance-weight-loader-seed-instance-service-port [seed_instance_service_port] \
  --remote-instance-weight-loader-backend transfer_engine
```

### ModelExpress as backend

[ModelExpress](https://github.com/ai-dynamo/modelexpress) is a coordination service that manages P2P weight transfer metadata. It removes the need for direct seed IP/port configuration by providing a centralized registry that instances publish to and discover from. The ModelExpress Python package must be installed in the SGLang image.

A running ModelExpress server is required. See the [ModelExpress documentation](https://github.com/ai-dynamo/modelexpress) for setup instructions.

server instance:
```bash Command
python -m sglang.launch_server [args] \
  --load-format remote_instance \
  --remote-instance-weight-loader-backend modelexpress \
  --modelexpress-config '{"url": "[modelexpress_grpc_host:port]", "transport": "nixl"}'
```

All SGLang instances use the same command shape. If no ready source exists, the instance loads weights natively and publishes metadata to ModelExpress. If a compatible source exists, it loads weights through ModelExpress P2P transfer. Set <code>"transport": "transfer_engine"</code> to use Mooncake TransferEngine instead of the default NIXL transport.

#### Releasing and reloading weights

When the server runs with `--enable-memory-saver`, `/release_memory_occupation` with the `weights` tag first tells ModelExpress to stop serving this instance as a P2P source. With the NIXL transport, ModelExpress waits for transfers that peers have in flight, so the call can take as long as the largest pending transfer. The `transfer_engine` transport does not wait for them.

What happens on `/resume_memory_occupation` depends on `--enable-weights-cpu-backup`:

- With the backup, the weights come back valid and the instance publishes itself as a source again.
- Without it, the weights are discarded. Resume the weights, then reload them before you resume the KV cache. The reload reads from another ModelExpress source, or from the checkpoint if no source is ready, and then publishes the instance again. It requires the NIXL transport.

```bash
curl -X POST http://HOST:PORT/resume_memory_occupation -H "Content-Type: application/json" -d '{"tags": ["weights"]}'
curl -X POST http://HOST:PORT/update_weights_from_disk -H "Content-Type: application/json" -d '{"model_path": "MODEL_PATH", "load_format": "remote_instance"}'
curl -X POST http://HOST:PORT/resume_memory_occupation -H "Content-Type: application/json" -d '{"tags": ["kv_cache", "cuda_graph"]}'
```

`model_path` must be the path the server was started with. `load_format` defaults to the format the server was started with, so you can omit it here; pass a disk format such as `auto` to load a different model instead. Updating weights is rejected while they are released.

Reloading through `remote_instance` reloads only the target model. With speculative decoding, start the server with `--enable-draft-weights-cpu-backup` so the draft weights survive the release; otherwise the reload is rejected.

ModelExpress does not track weights that change another way, such as through `update_weights_from_tensor`. After a release that discarded the weights, such a load leaves the instance unpublished. An instance that is still published, or that resumes from a CPU backup, keeps advertising the changed weights as the model it started with.
